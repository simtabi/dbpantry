The implementation has long since landed; this file is now the design record: identity, pins, the capacity table and the decision log. Everything below was verified during this session against live registries, the GitHub API, and — where prose was ambiguous or absent — against containers actually booted on arm64. Where a claim came from a doc page rather than an executed check, it says so.

## 7. Decision log

Every spec issue found, and how it was resolved. Entries marked **[needs your call]** are the ones worth your attention.

**D-01 — spec.md had no section 21.** The kickoff prompt required reconciling "section 21 (scale, HA, sync)" and producing its capacity truth table; the design doc ended at section 20. *Resolution:* authored section 21 from the verified HA research baseline and appended it to spec.md as an approved amendment (you approved this before I wrote it). Its requirements are folded into services, env, commands, CI, and acceptance above.

**D-02 — Three-way identity conflict.** SPEC line 5 says "repo laranail/multidb-server"; section 16 publishes to `ghcr.io/simtabi/`; the actual checkout is `simtabi/multidb-server`. *Resolution:* `simtabi/multidb-server` + `ghcr.io/simtabi/*`, per your call.

**D-03 — The backup sidecar moved namespace and the spec's reference is stale.** `tiredofit/docker-db-backup` is now published as **`nfrastack/db-backup`**. `tiredofit/db-backup` last published `4.1.100` on 2026-03-13; `nfrastack/db-backup` is at `4.9.0` (2026-07-30). *Resolution:* pin `nfrastack/db-backup:4.9.0` by digest; SPEC references updated in docs during phase 4.

**D-04 — [needs your call] The free tier caps backup jobs at 3, which is exactly our engine count.** The project moved to a sponsorware model: "*To unlock advanced features, one must provide a code…*" and "*A limit of 3 can be created when not in advanced mode.*" I verified by parsing every table in the README that **no environment variable is actually `Adv.`-gated** — S3, encryption, checksums, `EXTRA_BACKUP_OPTS` and `BACKUP_GLOBALS` are all free. The only real constraint is the **3-job ceiling**, and pg + mysql + mariadb is exactly 3, leaving zero headroom for a fourth job (a second PG major during a migration window, or an HA replica). *Resolution offered, your pick:*
  - **(a) Recommended — write our own sidecar.** SPEC section 11 already mandates "one dump helper, two callers", and section 6.1 already bakes `rclone` and `zstd` into every engine image. A thin cron container on `multidb-server-cli` driving that same script removes a third-party dependency, the sponsorware risk, and the job ceiling, at the cost of writing retention/notification logic ourselves (~150 lines).
  - **(b) Keep `nfrastack/db-backup:4.9.0`** and accept a hard 3-job ceiling, documenting that a 4th engine or migration-window job requires a sponsor code.
  I will implement (a) unless you say otherwise, and either way the shared dump helper is the single source of dump flags.

**D-05 — Floating tags on the backup image are currently arm64-only.** `nfrastack/db-backup:latest` and `:alpine_3.24` publish **only** `linux/arm64` right now; the versioned `4.9.0` and `4.9.0-alpine_3.24` are correctly amd64+arm64. An amd64 CI runner pulling `latest` would fail outright. *Resolution:* no change needed — CLAUDE.md's "pinned digests everywhere, no `latest`" rule already prevents this. Recorded because it is a live demonstration that the rule earns its keep.

**D-06 — [needs your call] pgjwt is unmaintained.** `michelp/pgjwt` has **no releases at all** and its last push was **2023-03-02**, over three years ago. It is not in PGDG. It is ~50 lines of plpgsql over `pgcrypto`. *Resolution offered:* vendor the SQL into `images/pg/initdb.d/` pinned to a specific commit, documented as vendored-and-frozen; or drop it from the default suite. I lean **vendor**, because it is trivial, arch-independent, and dropping it silently changes the spec's promised extension list. Say the word if you would rather drop it.

**D-07 — Four extensions are not in PGDG; none is an arm64 blocker.** `pg_graphql`, `pg_net`, `pgsodium`, `pgjwt`. *Resolution:* `pg_graphql` 1.6.1 publishes official prebuilt `.deb`s for **pg14–18 on both amd64 and arm64** — download, no build. `pg_net` 0.20.5 and `pgsodium` 3.1.11 build from source in a builder stage (both C, both portable). `pgjwt` per D-06.

**D-08 — The spec's arm64 worry was aimed at the wrong extensions.** It named `http` and `pg_partman` as at-risk. Both are in PGDG for arm64 (`1.7.2` and `5.5.0`, verified on a booted arm64 container). No workaround needed.

**D-09 — PostgreSQL will shut down uncleanly under s6 unless we override the stop signal.** The official postgres image sets `STOPSIGNAL SIGINT` (fast shutdown). s6 sends **SIGTERM**, which PostgreSQL interprets as *smart* shutdown — it waits for every client to disconnect voluntarily, so it hangs until `S6_KILL_GRACETIME` expires and then takes SIGKILL, forcing crash recovery on the next boot. This is silent: the container appears to stop normally. *Resolution:* the PG s6 service directory gets a **`down-signal`** file containing `SIGINT` (confirmed supported in the s6 service directory format, replacing SIGTERM for `s6-svc -d`). `make verify` gets a dedicated clean-shutdown check that asserts the next boot logs no recovery.

**D-10 — The official pgBouncer image is amd64-only and years stale.** `pgbouncer/pgbouncer:latest` is a single-arch (amd64) manifest at version **1.15.0**, while upstream pgBouncer is at **1.25.2**. It would break the arm64 half of the matrix and ship a very old pooler. *Resolution:* use **`edoburu/pgbouncer:v1.25.2-p0`** (multi-arch amd64+arm64, current upstream version).

**D-11 — Patroni publishes no production image.** The Patroni project ships only a Dockerfile and compose explicitly marked development-only. Spilo (`ghcr.io/zalando/spilo-NN`) is multi-arch and production-grade, **but it bundles its own PostgreSQL**, which would replace `multidb-server-pg` entirely and discard our extension suite, baked config, and certs — directly contradicting the spec's core premise. *Resolution:* layer **Patroni 4.1.4 (pip)** onto our own `multidb-server-pg` image as an s6 service, gated by the `ha` profile. Keeps one PG image across dev, prod, and HA. Costs us the Patroni bootstrap wiring that Spilo would have given free; that work lands in phase 7.

**D-12 — etcd pinned at `v3.6.6`**, multi-arch confirmed. Section 21 states the 3-node minimum explicitly, because a 2-node etcd has *lower* availability than a single node.

**D-13 — MariaDB 11.4 auto-TLS does not conflict with our CA (verified empirically).** I booted `mariadb:11.4.12` twice. With no certs configured: `have_ssl=YES`, `ssl_ca`/`ssl_cert`/`ssl_key` all **empty**, and **no `.pem` written to the datadir** — so zero-config SSL uses an **ephemeral, in-memory, per-start** certificate. With our CA-issued certs in `/etc/mysql/conf.d`: our paths are honoured exactly and `require_secure_transport=ON` works. *Resolution:* explicit certs take precedence; auto-generation only fills a gap. Documented consequence: clients **cannot** use verify-full against the ephemeral cert (it changes every restart), which is precisely why `make certs` and the mounted CA are mandatory rather than optional.

**D-14 — MariaDB's "latest 11.x" is now 11.8, and it is also LTS.** The spec's third MariaDB slot assumed a rolling non-LTS release. *Resolution:* offer `10.11` / `11.4` (default) / `11.8`, all LTS, all pinned. Strictly better than tracking a short-lived release.

**D-15 — MySQL 9.x innovation releases are short-lived.** Current is `9.7.2`. Innovation releases are superseded roughly quarterly and unsupported once replaced. *Resolution:* pin `9.7.2`, and document in upgrade.md that the 9.x slot is a preview track, not a deployment target; 8.4 LTS stays the default.

**D-16 — pgvector base distro choice.** Unsuffixed `0.8.6-pgNN` tags are Debian 12 **bookworm**; `-trixie` (Debian 13) variants exist. *Resolution:* build on **bookworm** now, because every PGDG extension version in section 4 was verified against `bookworm-pgdg`. A trixie migration is a tracked follow-up, not a phase-2 blocker.

**D-17 — MySQL and MariaDB do not share a base OS.** MySQL official images are **Oracle Linux 9**; MariaDB is **Ubuntu 24.04** (verified: `11.4.12-MariaDB-ubu2404`). Package managers, config paths, and available client tooling differ. *Resolution:* the two Dockerfiles cannot share a tooling layer; `images/mysql/` uses `microdnf`, `images/mariadb/` uses `apt`. Flagged because "baked-in conf.d + client tooling" in section 6 reads as though one recipe covers both. It does not.

**D-18 — `read_only` rootfs conflicts with every engine.** Section 9 asks for read-only root "wherever the engine tolerates it". PostgreSQL needs writable `PGDATA`, `/var/run/postgresql`, and `/tmp`; MySQL/MariaDB need `/var/run/mysqld` and `/tmp`; s6 needs `/run`. *Resolution:* `read_only: true` **with** an explicit tmpfs list per engine, proven by a `make verify` check that boots each engine read-only. If any engine fails that check it gets `read_only: false` with the reason recorded here rather than a silently dropped hardening claim.

**D-19 — Non-root and s6 as PID 1 interact.** s6-overlay must start as root to run its init stages (permissions, cert placement, conf assembly), then drop to the engine user via `s6-setuidgid`. A container-level `USER postgres` would break stage 1. *Resolution:* container runs as root PID 1 (s6), every long-running service drops privileges; `make verify` asserts no engine process runs as uid 0. This satisfies the intent of section 9 while being honest that the *container user* is root.

**D-20 — "No `latest`" vs. the spec's moving tags.** Section 6 lists tags `:9` and `:11`, which are moving aliases. *Resolution:* our published tags keep those friendly aliases, but every **upstream** base is pinned to an exact minor **and digest**; Renovate raises the bumps.

**D-21 — Supply-chain signing.** Section 9 says "signs images with cosign", while the Simtabi org convention settles on `attest-build-provenance` as the mandatory default with cosign optional. *Resolution:* build provenance attestation + syft SBOM are mandatory in CI; cosign is not added in v1 absent a named downstream consumer. Recorded so the SECURITY.md verification instructions match what CI actually produces.

**D-22 — Repo hygiene: `CLAUDE.md` was being silently excluded.** Your global gitignore (`~/.config/git/ignore:22`) ignores `CLAUDE.md`, so the first commit dropped it while committing `.DS_Store`. Since kit.md makes CLAUDE.md the contract that binds every session and git the memory between them, losing it would quietly break the whole loop. *Resolution:* repo `.gitignore` negates it (`!CLAUDE.md`), which wins over `core.excludesFile`; `.DS_Store` untracked and ignored.

**D-23 — Section 19 defaults applied unchanged**, per the kickoff prompt: no plpython3u (toggle available), Tailscale-first prod docs on generic Ubuntu LTS, S3 wiring present but disabled until credentials exist, `ghcr.io/simtabi` private until flipped, defaults PG 17 / MySQL 8.4 / MariaDB 11.4, no extensions beyond sections 5–6, public Laranail conventions only.

**D-24 — Every script must be bash 3.2 compatible, because macOS ships bash 3.2.** Found in phase 1 when `make lint` died with `mapfile: command not found`. macOS ships GNU bash **3.2.57** (the last GPLv2 release) and this machine has no Homebrew bash, so `mapfile` (bash 4.0), associative arrays (`declare -A`, bash 4.0), and friends are all unavailable. SPEC section 1 promises the toolkit works "identical across macOS, Windows, and Linux", so depending on a bash the platform does not ship would break that promise on the primary development platform — and it would have broken quietly, since CI runs Linux with bash 5. *Resolution:* every script is written to bash 3.2. Array building uses `while IFS= read -r` loops instead of `mapfile`; `check-env`'s port-collision tracking uses a plain string of `port:key` pairs instead of an associative array. A repo `.shellcheckrc` sets `source-path=SCRIPTDIR` so checks can source `lib.sh` through a dynamic path without tripping SC1091. Recorded because it is a standing constraint on every future phase, not a one-off fix.

**D-25 — pgsodium is held at 3.1.9, and no base image would fix it.** pgsodium 3.1.11 fails to compile on our base: `crypto_ipcrypt_NDX_KEYBYTES undeclared`. Its release commit is literally *"Add IP address encryption (crypto_ipcrypt) and bump to libsodium 1.0.2x"* — so 3.1.11 requires libsodium ≥ 1.0.20, while Debian 12 bookworm ships **1.0.18**. I checked whether moving to the trixie base (the D-16 follow-up) would fix it: **Debian 13 trixie ships the same 1.0.18**, so it would not. *Resolution:* pin `PGSODIUM_VERSION=3.1.9`, the last release that builds against 1.0.18, verified by compiling it. The only loss is the brand-new `crypto_ipcrypt` feature, which nothing in SPEC requires. Revisit when either Debian ships libsodium ≥ 1.0.20 or we vendor libsodium.

**D-26 — pg_graphql's .deb ships symlinks that would dangle, and that PG 18 would shadow.** The official package does not put its files in the extension directory: it installs them under `/var/lib/postgresql/extension` and symlinks them from `/usr/share/postgresql/<major>/extension`. Two independent failures follow. First, our builder stage copies only `/usr`, so the links dangle and PostgreSQL reports `Could not open extension control file … No such file or directory` **while `ls` shows the entry present** — a genuinely confusing signature. Second, and worse in production: **PG 18 mounts the data volume at `/var/lib/postgresql` itself**, so even a correct copy would be shadowed by the volume at runtime, and pg_graphql would vanish the moment a user switched majors. *Resolution:* the builder flattens those symlinks into real files and then asserts none remain. Caught by check 09, which is exactly the kind of failure that would otherwise have shipped.

**D-27 — Raising the s6 gracetimes made shutdown worse, not safer.** I set `S6_KILL_GRACETIME` and `S6_SERVICES_GRACETIME` to 30000ms reasoning that a database needs time to stop. Check 10 then failed with a 31s shutdown, and the timestamped log showed why: s6 brought PostgreSQL down cleanly, checkpoint and all, **in about one second** — then sat idle for the remaining 30s before PID 1 exited. The gracetimes do not give a service more time to stop (s6-supervise already waits indefinitely for a longrun to exit); they only govern how long s6 waits *after* everything is already down. *Resolution:* leave both at the s6 default of 3000ms; the database's real budget is `stop_grace_period` / `docker stop -t`. Shutdown went 31s → 4s. Worth recording because the intuitive setting is the harmful one.

**D-28 — Read-only rootfs needed two non-obvious fixes.** SPEC section 9 asks for `read_only` where the engine tolerates it, and D-18 promised an explicit tmpfs list. Two failures had to be fixed to get there, neither of which announces itself clearly:
  - **Docker mounts `--tmpfs` `noexec` by default.** s6 executes `/run/s6/basedir/bin/init`, so the container died at stage 0 with `Permission denied` and exit 126 — a signature that reads like file ownership and is not. `/run` and `/docker-entrypoint-initdb.d` need `exec`.
  - **The user bundle must live in `/etc/s6-overlay/user-bundles.d`, not `/etc/s6-overlay/s6-rc.d/user`.** The legacy location makes s6 *write* a `type` file under `/etc` during boot, which a read-only filesystem refuses. s6 had been printing a deprecation warning about exactly this from the first build.
  Generated state (conf, certificates) also moved to `/run/mdb/`, so the writable set is `/run`, `/tmp`, `/var/run/postgresql`, `/docker-entrypoint-initdb.d`, plus the data volume — and nothing under `/etc` or `/usr`.

**D-29 — D-17 was right about the divergence and wrong about what it costs.** I recorded in D-17 that MySQL (Oracle Linux 9) and MariaDB (Ubuntu 24.04) cannot share a tooling layer, and concluded the two images would need separate recipes. Probing them directly showed the divergence is narrower than that: the package manager differs (`microdnf` vs `apt-get`), the client binaries differ (`mysql`/`mysqladmin` vs `mariadb`/`mariadb-admin`), and the missing tools differ (MySQL lacks `procps`/`unzip`, MariaDB lacks `curl`) — but **both include `/etc/mysql/conf.d`, and MariaDB includes it last**, so one generated file dropped there configures either engine and still loses to a user override. *Resolution:* one shared set of init scripts and one shared s6 tree in `images/_shared/mysql-family/`, selected by a `MDB_ENGINE` baked at build time; only the two Dockerfiles differ. This required moving every image's build context from `images/<engine>/` to `images/`, which is why the PG Dockerfile's COPY paths changed too. Recorded because the original entry would have led a later phase to duplicate the whole script set.

**D-30 — The engine descriptor, and why the refactor came before the engines.** Adding MongoDB and Cassandra to a codebase with three hardcoded engines would have meant editing compose, backup, restore, new-project, check-env and a dozen checks per engine — six places to forget one. Engines are now declared in `engines/<name>/engine.conf` and read by generic machinery; family hooks in `engines/_family/<family>.sh` carry the few operations that genuinely need code. Descriptors were written for the three EXISTING engines first, deliberately: if they had not fitted, the abstraction was wrong, and that is far cheaper to learn before two more are built on it. They fitted. See SPEC section 22 and `docs/guides/architecture.md`.

**D-31 — Pooling is a capability, not a service every engine gets.** The request was "connection pooling for all database types". Researching it properly showed a uniform abstraction would be a lie: PostgreSQL *needs* pgBouncer (one OS process per connection, ~10 MB each), MySQL merely benefits from ProxySQL (thread-per-connection is far cheaper), and **MongoDB and Cassandra drivers pool natively** — an external proxy in front of either is an anti-pattern that breaks topology discovery and retryable writes for Mongo, and token-aware routing for Cassandra. The descriptor therefore declares `external` or `driver`, and where it says `driver` the answer is documentation (reuse one client per process), not infrastructure. Check 31 forces every engine to commit to one and explain it.

**D-32 — We publish only OSI-licensed artefacts; MongoDB is referenced, not derived.** My first recommendation was to publish an SSPL-derived MongoDB image with clear labelling, which is what most Docker toolkits do. The better rule: every artefact this project publishes is OSI-licensed, so a downstream user never has to reason about our supply chain. `MDB_ENGINE_PUBLISH=reference` means the upstream image is used directly and configured at runtime — MongoDB stays fully supported, and the licence obligation stays with MongoDB. It generalises: any engine that changes licence moves by flipping one field, with no artefact to withdraw. **FerretDB** was added as the OSI-licensed document alternative (Apache 2.0, MongoDB wire protocol, PostgreSQL storage), with its real gaps recorded in the descriptor rather than discovered later.

**D-33 — MongoDB defaults to 7.0, not the newest, because 8.x cannot start on modern kernels.** MongoDB 8.x refuses to start on Linux kernel 6.19+ ([SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912)). Verified here on kernel 7.0.14: **8.3.7 crash-loops, 7.0.39 runs**. That kernel is not exotic — OrbStack and current distributions ship it — so defaulting to 8.x would have handed a crash loop to a large share of users on first boot. 8.0 and 8.3 remain on the menu.

**D-34 — Both new engines ship insecure, and correcting that is the main value.** MongoDB runs with **no authentication** unless root credentials are supplied. Cassandra ships `AllowAllAuthenticator` **and** `AllowAllAuthorizer` — not weak auth, none, and no authorization either. Worse, merely enabling `PasswordAuthenticator` leaves a superuser named `cassandra` whose password is also `cassandra`: auth that is on with a publicly known credential is barely better than auth that is off. The Cassandra image now flips both settings, refuses to start if it cannot verify them, and rotates that default credential to the generated secret. Check 32 asserts across **every** engine that unauthenticated connections are refused, so a new engine inherits the guarantee by existing.

**D-35 — The pooler stores no application password; it resolves them with `auth_query`.** The obvious pgBouncer setup gives it a userlist of every user and password, making the pooler a second place every credential lives. Instead it has one login role of its own and looks verifiers up through a `SECURITY DEFINER` function, `pgbouncer.get_auth`, which returns a single row and **excludes superusers** — so compromising the pooler yields one credential rather than all of them, and never the superuser's. Its `search_path` is pinned to `pg_catalog`, because a `SECURITY DEFINER` function resolving unqualified names through the caller's path is the CVE-2018-1058 shape. The function is created by a new `mdb-converge` stage that runs on **every** start rather than only at first init, so enabling the pooler on an existing volume does not require destroying the data. Check 33 asserts the behaviour: eight clients collapse onto a pool of two, the userlist contains no application password, and a wrong password is still refused.

**D-36 — Cassandra rate-limits password changes, so provisioning tests the credential instead of resetting it.** The natural idempotent pattern — `CREATE ROLE IF NOT EXISTS ... WITH PASSWORD`, then `ALTER ROLE ... WITH PASSWORD` — fails **every** time on Cassandra, not intermittently: passwords may only be changed once per 5000 ms per role, and the server reports the refusal as `code=1001 [Coordinator node overloaded]`, which names neither the role nor the real cause. The hook therefore only alters a password when it is genuinely wrong, tested by logging in with it, and retries around the limiter when it must. Two other Cassandra-specific traps were found the same way and are recorded in the hook: `cqlsh -e` splits its argument on `;`, so a statement string beginning with a newline produces an empty leading statement and exits non-zero **after** running everything else; and `_cass_set_password` avoids a trailing `[ ] && sleep` list, which returns 1 on its last iteration and trips `set -e` in any caller that has not already neutralised it.

**D-37 — HA is a rehearsal topology, and the profile is the only switch.** Every node runs on one host, so the host is a single point of failure that Patroni cannot fix; what the stack gives you is a genuine election to practise on before you need one. Two design points came out of building it. First, `PROFILES=ha` is the *only* switch: a separate `MDB_HA_ENABLE` flag existed alongside it and gated nothing but a validation, so `PROFILES=ha` with the flag left false ran HA with no quorum check at all. Second, **HA replaces the `pg` profile rather than joining it** — HAProxy owns the PostgreSQL port and routes it to the current leader, so running both binds 5432 twice; `check-env` now compares *effective* ports, defaults included, because a default that collides is still a collision.

**D-38 — Four failures in the Patroni image, each reported as something else.** Worth recording because all four are silent in the same way. (1) The etcd host list written into `patroni.yml` as a comma-separated scalar is a YAML parse error at the first comma: Patroni exits before contacting etcd and the container merely looks unhealthy. (2) Dropping `mdb-postgres` from the s6 bundle is not enough, because s6 starts anything a remaining service *depends* on and `mdb-exporter` depends on it — the upstream entrypoint then ran alongside Patroni against the same data directory and died on a missing `POSTGRES_PASSWORD`. (3) The data volume must be mounted one level *above* the data directory: Patroni renames that directory when bootstrapping a replica, and a mount point cannot be renamed ("Device or resource busy", while the leader looks fine). (4) `s6-setuidgid` changes the uid but not the environment, so `HOME` stayed `/root`; libpq could not read `/root/.postgresql/`, treated that as a failed TLS start, and **retried unencrypted**, which the `hostssl` replication rule correctly refused — the only visible error named the pg_hba rule.

**D-39 — A failover budget at or below Patroni's `ttl` is unreachable by construction.** The check budgeted 30s against Patroni's default `ttl` of 30s: the leader lock does not expire until the ttl elapses, so no election can *begin* inside the budget however healthy the cluster is. Retuned to `ttl 20 / loop_wait 5 / retry_timeout 5` (Patroni requires `ttl >= loop_wait + 2 × retry_timeout`) with a 60s budget; real failovers now complete in ~20s. Lower is not automatically better — a short ttl makes a brief stall look like a dead leader, and demoting a healthy primary costs more than a few seconds of failover. Relatedly, Patroni will not promote a replica lagging more than `maximum_lag_on_failover`, so **if every replica is behind there is no election at all** and every node logs "I am not the healthiest node". That is correct behaviour, and the check now waits for genuine catch-up before killing the leader rather than reporting it as a broken failover mechanism.

**D-40 — ProxySQL holds password *verifiers*, which is why it could be shipped at all.** I first declined to wire ProxySQL, on the grounds that it has no equivalent of pgBouncer's `auth_query` and would therefore have to store every application password — giving up on MySQL, where pooling is not even necessary, the property D-35 goes to some trouble to preserve. That reasoning was half right and the conclusion was wrong. ProxySQL cannot look a credential up on demand, but what it stores can be the **verifier**: the `caching_sha2_password` hash copied straight out of `mysql.user.authentication_string`, so the pooler knows no more than the server already does. Copied as HEX and reassembled with `UNHEX()` because the value is binary, which is also why configuration goes through the admin interface rather than a `.cnf` — `UNHEX()` is a SQL function and a config file cannot express it. Three supporting decisions: the pooler gets its **own narrow account** (`SELECT` on `mysql.user`, `REPLICATION CLIENT`, nothing else) created by a new MySQL-family convergence stage, because root is restricted to the local socket and that hardening is not worth relaxing; the admin interface on 6032 is **never published**, since it can read every verifier held; and check 35 asserts the stored value carries the `$A$` verifier prefix and does not contain the password, without which this integration would be a security regression over not having it.

**D-41 — Compose profiles are OR, so `pooler` is expanded before compose sees it.** A single shared `pooler` profile starts *every* pooler, including those whose engine was not selected, and compose then rejects the entire project with "service mariadb-pooler depends on undefined service mariadb". Compose has no way to express "pooler AND mysql". Each pooler therefore has its own profile (`pg-pooler`, `mysql-pooler`), and `scripts/profiles` expands `pooler` into the ones matching the selected engines — so the documented `make up PROFILES=pg,pooler` keeps working without compose needing AND semantics.

**D-42 — pgBackRest closes PITR and off-site in one dependency.** The alternative was a hand-rolled `archive_command` copying WAL somewhere, which gets you archiving and nothing else — no retention, no verification that the archive is replayable, no repository format that restore understands. pgBackRest gives WAL archiving, an S3-compatible repository, encryption at rest and `check` from one package. Off by DEFAULT because archiving on a laptop fills a disk with segments nobody will replay; **required** in prod, along with `repo1-type=s3`, because a posix repository lives on the machine it is protecting. The repository gets its own volume, not a directory inside PGDATA, and is not per-major: a backup taken before an upgrade is exactly the one wanted after a failed upgrade. Two failure modes were found building it and are recorded in the code — a convergence stage that exited early on an unrelated missing secret and so silently skipped PITR entirely, and `%%p` in a printf format reaching postgresql.conf as an escaped literal, which handed pgbackrest the two characters `%p` instead of a WAL path and hung the first backup forever.

**D-43 — The vulnerability scanner is a pinned binary, not the trivy action.** In March 2026 an attacker force-pushed 75 of `aquasecurity/trivy-action`'s 76 version tags to steal CI secrets. Referencing it by tag is exactly the supply-chain risk a scanner exists to reduce, so CI downloads the trivy binary at a pinned version and verifies it against the release checksums — the same reasoning that pins every base image by digest, applied to the thing doing the scanning. Scanning fails the build only on HIGH/CRITICAL **with a known fix**: unfixed findings are reported but tolerated, because a scanner that cannot be made green stops being read. Waivers must justify themselves — check 38 rejects a bare CVE ID, a stub reason, or a waiver with no revisit condition, and also fails if CI stops scanning or stops honouring the ignore file, which is the pairing that rots.

**D-44 — An off-site setting that silently does nothing is worse than none.** `MDB_S3_BUCKET` and its credential files were documented in `.env.example` and `push_s3` read none of them: it ran `rclone copy :s3:` with no configuration, failed, and the failure was swallowed by a log line while `backup-all` reported success. That is the worst shape a backup bug can take, because everything looks configured. rclone is now given credentials from the `_FILE` secrets, and a failed push **aborts the backup** rather than being logged. Check 39 asserts the wiring rather than needing an object store: every documented setting is read, credentials are exported, and no tolerated-failure form remains.

**D-45 — Point-in-time recovery targets a binary-log COORDINATE, not a timestamp.** The obvious interface is `--to '2026-08-09 12:00:00'`, and it is quietly broken: `mariadb-binlog` given several files and `--stop-datetime` **exits after the first file and silently skips the rest** ([MDEV-35528](https://jira.mariadb.org/browse/MDEV-35528)). A time-bounded replay therefore recovers almost nothing while reporting success — in testing it emitted 41 lines and no `CREATE DATABASE`, cutting events whose timestamps were demonstrably earlier than the target. Positions have no such bug, no second-granularity ambiguity, and no timezone interpretation, and `--stop-position` applies to the **last file named**, which is exactly the semantics recovery needs: every earlier file replays in full and the final one stops at a byte offset. So `make pitr-restore ENGINE=mariadb TO=binlog.000002:873`, with `make pitr-info` printing the current coordinate and dumps recording theirs. Check 40 proves it end to end.

**D-46 — MySQL claims PITR by extracting one file from a package it cannot install.** The official image is `mysql-community-server-minimal` on Oracle Linux 9 and ships no `mysqlbinlog`, so a binary log could be written and never replayed — an audit trail, not a recovery path. Installing `mysql-community-client` does not work: it also owns `/usr/bin/mysql`, `mysqladmin` and `mysqldump`, and rpm refuses the file conflicts with server-minimal. Six routes were tried before the one that works — the OL9 `mysql` 8.0 client (same conflict), `mysql-community-client` from the enabled repos (absent; the image points at MySQL's *docker* subtree, which carries only server-minimal), MySQL Shell (present, but 8.4.10, and `util.dumpBinlogs`/`loadBinlogs` arrived in Shell 9.2), third-party images carrying the binary (unpullable here), and the generic tarball (no arm64 *minimal* variant). The answer is to fetch the matching client RPM and extract **only** `/usr/bin/mysqlbinlog` from it: no package is installed, nothing conflicts, and nothing else from that package enters the image. Its version is read from the installed server with `rpm -q` rather than pinned, because `mysqlbinlog` must read what this exact server writes and a pinned version would drift silently the first time the base image bumped.

**D-47 — The coordinate statement is spelled three ways, so all three are tried.** MySQL 8.4 **removed** `SHOW MASTER STATUS` in favour of `SHOW BINARY LOG STATUS`; MariaDB added `SHOW BINLOG STATUS` and kept the old name as an alias. Branching on a version string would need updating at every release, so `scripts/pitr` and check 40 try the three in order and use the first that answers. This is the kind of divergence that makes a single-engine check worthless: MariaDB passed on `SHOW MASTER STATUS` while MySQL aborted on it, so check 40 now exercises **both** engines by default.

**D-48 — pgBouncer is built here, not pulled from a third party (supersedes D-10).** D-10 chose `edoburu/pgbouncer` because the vendor's own image is amd64-only and stuck at 1.15.0. That solved the architecture problem and left this toolkit's only community rebuild in the supply chain — an organisation that can be compromised independently of pgBouncer itself, and whose update cadence we do not control, which is the same argument that pins every other reference by digest. `images/pgbouncer/Dockerfile` now builds it from a Docker Official base plus the **PGDG** package, maintained by the PostgreSQL project: current version, both architectures, no third party. The image also carries its own `ENTRYPOINT`, which the replacement initially did not — `docker run` then fell through to the base image's shell and exited 0, a container that "started successfully" having done nothing, and precisely the failure check 33 exists to catch. `docs/reference/image-provenance.md` records every image and its publisher, and check 42 fails the build on any namespace that is neither a Docker Official Image nor the upstream project's own.

**D-49 — Publishing a host port is a decision, not a default.** A modest profile set published **ten** host ports, which is ten chances to collide with something already on the machine — and every collision surfaces as a Docker error at the very end of a boot, naming neither the setting nor the process. `MDB_PUBLISH` now takes `none` (the default: publish nothing, applications join the network and use service names, which is what `make new-project` has always printed), `direct` (the old behaviour) or `proxy` (one front door owns the ports). In the latter two, a port is `MDB_PORT_BASE + offset`, so a collision is fixed by moving one number rather than hunting per-engine variables. The offset is **explicit in each descriptor**, not derived from the engine's own port: MongoDB's 27017 plus a 54000 base is 81017, past the end of the port range, and derived offsets would also shift when an engine is added. Check 31 asserts they are unique.

**D-50 — Caddy gets the layer4 module so one front door can serve raw TCP.** Caddy proxies HTTP natively and databases do not speak it, so `proxy` mode needs [caddy-l4](https://github.com/mholt/caddy-l4), built with xcaddy from Caddy's own official builder image — the same shape as the pgBouncer build. Two constraints came out of it. caddy-l4 v0.1.2 requires Caddy **2.11.4** exactly, so both stages moved together; a 2.10.2 builder fails the module graph outright. And the generated routes must sit inside a `layer4 { }` global option — emitted bare, Caddy parses each as a global option and rejects the whole config with *"unrecognized global option: :54004"*, which names the port rather than the missing wrapper. caddy-l4 is pre-1.0 and its author says to expect breaking changes, which is precisely why the default is `none` and `direct` remains: the proxy is a convenience, and nothing here depends on it to function.

**D-51 — gosu, rclone and postgres_exporter are rebuilt from their release tags, not waived.** All three were the newest upstream releases, and all three carried HIGH findings that had been fixed elsewhere. gosu 1.19 dates from 2025-09 and was compiled against a Go standard library with fifteen CVEs fixed since. postgres_exporter 0.20.1 was built the same way and also vendors `golang.org/x/net` and `golang.org/x/crypto` below their fixes. rclone 1.75.1 vendors a gRPC pseudo-version older than the CVE-2026-84445 fix. The previous answer was 26 expiring waivers, due to lapse on 2026-11-09 and fail every build. Each image now has a `gotools` stage that clones the same tag, raises only the named vulnerable modules (`go get module@fixed`, then `go mod tidy`), and builds on the toolchain pinned in `images/bases.tsv` (row `toolchain go`), which `scripts/build` passes as `GO_IMAGE`. It runs on `$BUILDPLATFORM` and sets `GOARCH` from `TARGETARCH`, so arm64 is cross-compiled rather than emulated. gosu lands on the base image's own path, so the upstream `docker-entrypoint.sh` and our convergence scripts call it unchanged. Every image proves the result at build time: `gosu nobody true`, `rclone version`, `postgres_exporter --version`. Check 02 fails if a Dockerfile's `GO_IMAGE` default disagrees with the bases row, since that default is what a bare `docker build` uses. Sources: [tianon/gosu 1.19](https://github.com/tianon/gosu/releases/tag/1.19), [rclone v1.75.1 go.mod](https://github.com/rclone/rclone/blob/v1.75.1/go.mod), [postgres_exporter v0.20.1 go.mod](https://github.com/prometheus-community/postgres_exporter/blob/v0.20.1/go.mod), [Docker `--platform=$BUILDPLATFORM` cross-compilation](https://docs.docker.com/build/building/multi-platform/#cross-compilation).

**D-52 — microdnf is not dnf, and that is now enforced rather than remembered.** Hardening the MySQL images meant removing one package and updating the rest, and both attempts reached for a dnf option microdnf does not have: `remove --noautoremove` (to stop rpm collecting `openssl-libs` along with `mysql-shell`) and then `update --exclude='mysql*'` (to stop the update pulling a newer server out from under the digest pin). microdnf is a deliberately minimal client and rejects an unknown option outright — at build time, on a runner, minutes into a matrix job — so each cost a full CI round, and the second broke two engine versions that had just gone green. `--exclude` has been requested since 2020 ([microdnf#119](https://github.com/rpm-software-management/microdnf/issues/119)) and does not exist. **D-53 — No container may depend on the host uid of a generated file.** Three services failed on CI and nowhere else, with three different symptoms and one cause: `make init` generates `secrets/` (0700, files 0600) and `certs/` on the host, owned by whoever ran it, and on Linux that ownership is exactly what a container process sees. Patroni's leader died on `server.key` ("must be owned by the database user or root") and the replicas waited forever for a primary, reported as a different unhealthy node each run. pgAdmin — the only container that reads a secret as a non-root user (uid 5050) with no root phase — crash-looped on its password file and Caddy answered 502. pgBouncer, whose image baked `USER postgres`, printed `cannot read /run/secrets/pgbouncer_password.txt` and exited 1. On macOS the Docker implementation flattens ownership, so all three worked on the machine they were written on; that is what made the class invisible.

Compose's `uid`/`gid`/`mode` fields on file-backed secrets are not the fix: outside swarm they are silently ignored ([docker/compose#9648](https://github.com/docker/compose/issues/9648); the PR to honour them, [#12625](https://github.com/docker/compose/pull/12625), was closed unmerged). A first pgAdmin fix set them, verified only that compose accepted the syntax — on macOS, where the failing condition cannot occur — and changed nothing.

The rule that follows: **our images read secrets as root and drop privileges at exec** (Patroni stages certs with `install -o postgres`; pgBouncer now starts root and drops via `setpriv` — the `USER postgres` directive was what forced the unprivileged read). For **third-party images that start unprivileged** (pgAdmin), the secret is mounted per-file — stepping around the 0700 directory — and generated world-readable, with the 0700 directory as the host-side guard; `render-config` heals the mode on existing checkouts because `init` refuses to run twice. And `scripts/build` now accepts derived image names explicitly: `scripts/build pgbouncer` used to match nothing, build zero images and exit 0, which cost one full round of testing against a stale image.

**D-56 — Releases are published by a tag-driven workflow that gates before it pushes.** `docs/guides/release.md` set the contract before any automation existed; `.github/workflows/release.yml` (2026-11-01) implements it rather than reinterpreting it. **D-57 — Each engine maintains its current and latest version, and any other runs only by explicit, unsupported choice.** The owner set the policy on 2026-11-01, after Cassandra 4.1's last waiver came due: across every engine, maintain only the newest supported line and the one before it, confirmed from each project's own end-of-life page, and keep older versions possible through a configurable override marked unsupported. Every version on a menu costs a digest pin, a build on two architectures, a Trivy gate, the acceptance checks, and a waiver whenever its upstream stops shipping fixes; the menu had grown to sixteen versions across six engines, several of them on their way out upstream. Where an engine runs a long-term track beside a short-lived one, the two lines are the two newest long-term releases, because a line supported only until the next quarterly release would leave the menu every quarter. The result, from 16 versions to 11: PostgreSQL 15 · 16 · 17 · 18 → **17** · 18 (five-year community support; 18 to 2030-11-14, 17 to 2029-11-08). MySQL 8.0 · 8.4 · 9.7 → **8.4** · 9.7, the two LTS lines (8.0 left Premier and Extended Support in April 2026; Innovation releases are supported only until the next). MariaDB 10.11 · 11.4 · 11.8 → **11.8** · 12.3, the two newest LTS lines (12.3 to 2029-06-12, 11.8 to 2028-06-04; 13.x is rolling), and the default moves from 11.4 to 11.8. MongoDB 7.0 · 8.0 · 8.3 → **7.0** · 8.0 · 9.0: the two newest Major Releases (9.0 to 2031-10-31, 8.0 to 2029-10-31; 8.3 is a Minor Release, patched only until the next), plus 7.0 (to 2027-08-31) as the default, the one exception the policy carries, explained below. Cassandra 4.1 · 5.0 → **5.0**. FerretDB stays at 2.

*The MongoDB default.* 7.0 stays the default and on the menu, the one exception to the two-line rule. 8.0 and 9.0 refuse to start on Linux kernels 6.19 to 7.0.13 (SERVER-121912, D-33): they vendor Google's TCMalloc, whose per-CPU caches use rseq, and those kernels can crash it. 8.0.30 and 9.0.4 exempt kernel 7.0.14 and later (SERVER-125742), and 8.0.34 and 9.0.4 were booted on OrbStack's 7.0.14 for this decision, but the exemption reads `uname -r`, and Ubuntu reports every 7.0 kernel as 7.0.0 whatever fixes it carries ([SERVER-136848](https://jira.mongodb.org/browse/SERVER-136848)). So no 8.x or 9.x release starts on Ubuntu 26.04's kernel, or on GitHub's ubuntu-24.04 runners, which moved to 7.0.0-azure in October 2026: the first CI run of this change failed check 32 on both architectures with exactly that message. 7.0 uses gperftools TCMalloc, which never calls rseq, and is unaffected. Setting `GLIBC_TUNABLES=glibc.pthread.rseq=1` gets 8.x past the check, but only by turning off a guard against a crash MongoDB says is real, on kernels whose fix cannot be read from the version, so it is not done. 7.0 leaves the menu, and the default moves to 8.0, when MongoDB reads the real kernel version or Ubuntu's kernels report it, or on 2027-08-31, whichever is first; whoever runs a kernel reporting 7.0.14 or later picks 8.0 or 9.0 today.

*The override.* A version off the menu needs `MDB_<ENGINE>_BASE_IMAGE`: the upstream image to build it from, or for MongoDB to run, pinned by digest. `check-env` refuses an off-menu version without it, so a typo cannot select an unmaintained engine, and refuses a tag without a digest, so an unsupported version is still a reproducible one; with it, `check-env` warns on every start that the version is unsupported, with no scan guarantee. `scripts/build` and the generated compose file pass it as `BASE_IMAGE` (compose previously built every version from the Dockerfile's default base), `scripts/build` labels the image `io.simtabi.dbpantry.support=unsupported`, and the Cassandra build keeps upstream's JARs for a series `jars.tsv` has no rows for instead of failing. A `.env` that names a version leaving the menu now fails `check-env` loudly, and its per-major volume is untouched; `docs/runbooks/upgrade.md` shows how to build the old image once through the override so `make upgrade` can read it. Moving checks 14 and 29 to 17 → 18 found that `make upgrade` mounted PostgreSQL 18 at `/var/lib/postgresql/data`, which 18 no longer uses, so it restored into an anonymous volume; it now mounts each side at its own path. Check 29 also runs under its own Compose project now, because it removes the volumes it uses and the default project's `mdb_pg17_data` is the operator's.

*Cassandra 4.1.* 4.1 is still maintained upstream, until 7.0 ships, so dropping it is an exception to the policy rather than a result of it. It vendors snakeyaml, and CVE-2022-1471 is fixed only in 2.0, which removed constructors 4.1's `YamlConfigurationLoader` calls (D-55). The last waiver, scoped to `snakeyaml@1.33`, was due to expire on 2026-11-09. Five ways out were weighed. *Keep waiving*: the finding is reachable only through `cassandra.yaml`, which the toolkit mounts and an attacker able to change already controls the node — `YamlConfigurationLoader` builds its parser with the full `Constructor`, and `verifyReplacements` reads the raw file through `new Yaml()` — so a VEX statement of `vulnerable_code_cannot_be_controlled_by_adversary` is arguable, but it is an argument that never expires, which is what the waiver format exists to prevent. *Backport the loader*: CASSANDRA-18875 moved 5.0 to snakeyaml 2.1; the change applies to 4.1 as a patch, but that means building Cassandra from source and shipping a 4.1 Apache never released. *A newer 2.x on 4.1*: CASSANDRA-20848 records that 4.1 cannot take snakeyaml 2.4 either. *Wait for upstream*: CASSANDRA-18614, the 4.1 ticket, is open with no fix version, and CASSANDRA-20928 moved snakeyaml to 2.4 for 6.0 alone. *Drop 4.1*: chosen. 5.0 ships snakeyaml 2.1 and is unaffected, and a 4.1.12 → 5.0.9 migration was rehearsed on 2026-11-01 — `nodetool drain`, the 4.1 volume copied, 5.0.9 booted on the copy, `upgradesstables` clean, 200 of 200 rows, 5.0 in `storage_compatibility_mode: CASSANDRA_4`, and the 4.1 volume unchanged — which is the procedure in `docs/runbooks/upgrade.md`. `.trivyignore.yaml` has no Cassandra entries.

*Roadmap — Cassandra's second line.* No 4.1 release with snakeyaml 2.x is planned: 4.1's build still pins snakeyaml 1.x and records 2.4 as incompatible, and the upgrade to 2.4, [CASSANDRA-20928](https://issues.apache.org/jira/browse/CASSANDRA-20928), was fixed for 6.0 only. So Cassandra regains a second line through 6.0, not 4.1. When 6.0 reaches GA it joins the menu as the latest beside 5.0 — a `cassandra 6.0` row in `images/bases.tsv`, `6.0` in the descriptor, a `jars.tsv` series for it, and D-55's bytecode and boot checks run against it — and the release that adds it says so. 4.1 returns only if a 4.1 release does ship snakeyaml 2.x with no other finding needing a waiver; its `jars.tsv` rows from 0.1.x are in git history. A source-built 4.1 is not on the roadmap.

*Keeping it current.* When a new line ships, the oldest maintained one leaves the menu in the next release and the CHANGELOG says so; `docs/guides/versions.md` holds the table and its sources. CI's build matrix is derived from the descriptors and `images/bases.tsv`, so a version change is those two edits. **D-60: one runtime layer, so dbpantry runs on Docker, Podman and nerdctl.** On 2026-11-02 the owner asked for dbpantry to work with "any containers like podman". Every script called `docker` or `docker compose` directly (about 50 files). The audit also found five places that only worked on Docker:

- short image names, which Podman rejects without a search registry;
- `podman build`'s OCI default, which drops HEALTHCHECK;
- `ps --format '{{.Service}} {{.Health}}'` templates, which differ between Compose implementations;
- `scripts/scan` bind-mounting `/var/run/docker.sock` into Trivy;
- Caddy's default ports 80/443, which a rootless runtime can't bind.

The fix is one sourced layer, `scripts/runtime-lib.sh`, plus `scripts/runtime` as its CLI. `CONTAINER_RUNTIME` chooses the runtime. Each runtime is an adapter, `scripts/runtimes/NN-<name>.sh`, that registers itself and defines hooks (`present`, `reachable` and `compose` are required; `ctr`, `alias`, `validate`, `build`, `rootless` and `provider` are optional). The core names no runtime. `auto` picks the first adapter, in filename order (today docker, podman, nerdctl), whose engine answers, and an adapter's `alias` hook lets the podman-docker shim count as Podman. The adapter design came from the owner's 2026-11-02 follow-up: more backends will be added, so adding one has to mean adding a file. `MDB_COMPOSE` overrides the Compose command, and detection is lazy and cached. Through that layer:

- `mdb_ctr` and `mdb_compose` replace the direct calls.
- `mdb_build` adds `--format docker` on Podman.
- Service state is read from `ps -q` plus `inspect` (Compose labels and `.State.Health`), which every implementation answers the same way.
- `mdb_compose_up_wait` polls health where `--wait` doesn't exist.
- For podman-compose and nerdctl, `COMPOSE_FILE` and `COMPOSE_PROFILES` are passed as explicit flags.

Other changes:

- The scan saves the image to a tarball and runs `trivy --input`, so no socket is mounted on any runtime.
- Every image reference is fully qualified (`docker.io/library/...`).
- `check-env` refuses ports below 1024 on a rootless runtime.

Products that speak the Docker API (OrbStack, Colima, Docker Desktop, Rancher Desktop's moby) are `docker`, with no code path of their own, and get documentation and testing notes instead. Kubernetes, LXC/LXD/Incus and Apple's `container` tool are planned as follow-up adapters. None of them is a Compose runtime, so each will also need a deployment path of its own. That is the reason for the adapter interface rather than more `case` branches.

Some things were deliberately not done:

- `docker-compose.yml` keeps its name. Every Compose implementation reads it, and renaming it would churn every doc and operator habit for nothing.
- SELinux `:z` labels are not added to bind mounts. Relabelling the checkout would relabel the operator's own files, so `docs/guides/runtime-podman.md` gives the one-time `chcon` or `label=false` instead.
- CI stays on Docker.

Two latent bugs surfaced while testing on a second checkout:

- The Makefile exported `COMPOSE_PROJECT_NAME ?= mdb`. Compose ranks the environment above `.env`, so a checkout naming itself `mdbrt` in `.env` still ran as `mdb` and attached the first checkout's volumes. The Makefile now reads the name from the env file, and scripts use `mdb_project_name`.
- Check 41's `docker rm -f` scan could never match.

Real Podman testing (6.1, a rootful `podman machine` on macOS) found a third problem. `podman compose` hands its provider the machine's API socket and ignores `CONTAINER_CONNECTION`, while the CLI follows the connection. A rootless connection on a rootful machine therefore created containers in one store and looked for them in the other. The Podman adapter's `validate` hook refuses that combination and names the three fixes.

Checks 48 (detection against stub CLIs, the adapter interface with a plugged-in fake backend, the project name, no direct CLI calls) and 49 (fully-qualified images) keep this true. The same session adopted the owner's env-file rule: values with whitespace or special characters are double-quoted, and every reader goes through `scripts/env-lib.sh` (`mdb_env_get`/`mdb_env_quote`), because the dozen `grep | cut -d= -f2-` readers would have returned the quotes as part of the value. Check 50 enforces both halves. Guides: [docs/guides/runtimes.md](docs/guides/runtimes.md).

**D-61: Markdown file names are lowercase slugs, except git and GitHub conventional files.** On 2026-11-02 the owner set a standing rule that Markdown files use lowercase slug names, and the same day narrowed it: files whose names git, GitHub or an agent tool looks for stay upper case. Those are `README.md` (at every level, so `rls/README.md` and `scripts/runtimes/README.md` too), `CHANGELOG.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, `LICENSE`, `CLAUDE.md` and `.github/PULL_REQUEST_TEMPLATE.md`, matching the exemptions in the owner's sim-standards pre-commit hook. Everything else was renamed in one commit with every reference updated: `design.md`, the runbooks, `docs/reference/spec.md` and `kit.md`, `docs/reorganization-plan.md`. A brief first pass also lower-cased README, CHANGELOG and the PR template; they were renamed back in a separate commit. Because macOS filesystems are case-insensitive, a stale link with the wrong case would still resolve there and fail only on Linux and on GitHub, so check 46 compares names case-sensitively.

**D-62: a backend layer between the scripts and the deployment, so dbpantry can run beyond Compose.** On 2026-11-02 the owner asked for Kubernetes, Incus and Apple `container` support. The plan for it (the backends design) was a working document that was never committed; its six phases, each now recorded here, were: **0** this backend layer (D-62); **1** Apple `container`, reached through socktainer as the docker runtime rather than as a backend (D-63); **2** Kubernetes through a Helm chart driven from `.env` (D-64); **3** PostgreSQL HA and scheduled backups on Kubernetes (D-65); **4** Incus through incus-compose (D-66); **5** operators for the other engines, as documentation and a values stub (D-67). D-60 made the container CLI pluggable, but every script still reached a database through `docker compose exec <service>`, which only exists where Compose does. Phase 0 adds a second axis, `MDB_BACKEND=compose|kubernetes|incus` (environment, then `.env`, default `compose`), next to `CONTAINER_RUNTIME`. Scripts talk to services, never to containers: `mdb_svc_exec [-u USER] SVC CMD` (21 call sites in backup, restore, pitr, ha, new-project, rotate-secrets and certs-renew), `mdb_be_running`, `mdb_svc_health`, `mdb_be_volumes`, `mdb_be_volume_rm`, plus `up`, `down`, `status` and `logs`, which `scripts/runtime` and the Makefile (`make down/status/logs/psql/mysql/...`) now use. Each backend is a file in `scripts/backends/` implementing those verbs; a verb a backend lacks fails by name instead of falling through to Compose. Scripts that cannot work elsewhere yet (`pitr restore`, `upgrade`) say so up front with `mdb_backend_require compose`. The Compose backend maps each verb to exactly the command scripts ran before, so nothing changes for existing users: check 52 asserts that mapping through a stubbed `mdb_compose`, along with the verb contract, the selection rules and that no `compose exec` remains outside the layer. Real runs on OrbStack with a scratch project (checks 21, 22, 27, 28, 41) pass unchanged. Testing found the library referenced `MDB_BACKEND_DIRS` unguarded, which killed every verify check under `set -u`; check 52 now sources it under `set -u`. Recovery volumes are recognised by `*_pitr` (Compose) or `pitr-*` (the Kubernetes PVC naming), so `make destroy` keeps them on both.

**D-63: Apple container is reached through socktainer, as the docker runtime.** The backends design weighed a native `container run` backend against socktainer, a third-party daemon serving the Docker API on top of Apple's `container`; the owner approved third-party tools. With socktainer, Compose, every script and every check run unchanged, so Apple container needs no backend of its own: the Docker adapter recognises it (a `.socktainer/` socket in `DOCKER_HOST` or the context, or `socktainer` in `docker version`'s server components) and reports `apple-container (socktainer)`. Two things differ and are handled. Each container is a VM whose memory is fixed at creation, 1 GiB by default, while PG tunes `shared_buffers` from `MDB_PG_MEM_LIMIT` (4g → 1GB); `compose.apple.yml` sizes each engine's VM from its limit, and the adapter's `validate` hook refuses socktainer without it rather than run PG with its whole VM as buffers. socktainer builds with BuildKit's docker-container driver, which keeps results in the cache, so the adapter's `build` hook passes `--load`. Tested on macOS 27.2 with container 1.6.1 (Homebrew; the machine had Apple's 1.5.0 .pkg, left in place) and socktainer 1.6.0: checks 08, 21, 22, 28 and 41 pass, and the VMs came up at 4096 MB (PG) and 2048 MB (MySQL). Not run there: MongoDB, Cassandra, HA, the UIs, TLS. Check 53 covers detection, the refusal and the build flag against a stub CLI.

**D-64: Kubernetes is a Helm chart driven from `.env`, deployed only to a named context.** Phase 2 of the backends plan; the owner required it to work on real clusters, not only local ones. `deploy/helm/dbpantry` runs one StatefulSet per engine with the Compose hardening (no privilege escalation, `cap_drop: ALL` plus the same five capabilities, `RuntimeDefault` seccomp), probes copied from the image healthchecks, `data` and `pitr` claims retained on uninstall, a NetworkPolicy limited to the namespace and a ServiceAccount with no token. Services carry the Compose service names, so an application's `host=pg` is the same on both. The backend (`scripts/backends/kubernetes.sh`) implements every verb with kubectl and helm, always pinned to `--context` and `--namespace`. `MDB_K8S_CONTEXT` is required, so dbpantry never deploys to the current context by accident. Configuration stays in `.env`: `scripts/helm-values` reads each engine's `environment:` block from `compose.engines.yml` and resolves it the way Compose does. A new engine variable therefore reaches Kubernetes with no second list to keep in sync. This deliberately does not extend `env-render`, which is the template interpolator (SPEC section 13), not a config mapper. Three deviations are documented in docs/guides/kubernetes.md: there is no Ingress (the database protocols are not HTTP), there is no `nofile` ulimit (Kubernetes cannot set one), and only baseline Pod Security is met, because the images drop privileges from root as they do under Compose. Testing on OrbStack (Kubernetes 1.35) and kind 0.33 found four bugs, all fixed:
- `helm uninstall --wait` returns before the pods stop, and a terminating pod still reports Ready, so `make destroy` refused, correctly, to delete volumes under a "running" stack. `down` now waits for deletion, and terminating pods are never running.
- MongoDB's upstream entrypoint reads its password file as `mongodb`, so its Secret is mounted 0444; the others stay 0400.
- The Cassandra image `chmod`ed its read-only overrides mount and stopped. It now leaves an existing directory alone.
- Helm 4 does not fall back from an unreachable IPv6 address the way kubectl does. This is an environment issue, and is documented.

Tested end to end on both clusters: up, psql and mysql through `kubectl exec`, `-u` user switching, backup into `backups/` and restore, port-forward, down with data kept, up with data back, and destroy keeping `pitr-*`. On kind, all five engines ran, including MongoDB authentication. Check 54 covers the values mapping, the verb contract against stub kubectl and helm, and the chart's rendering.

**D-65: PostgreSQL HA on Kubernetes is Patroni by default, CloudNativePG on request; backups are CronJobs with retention inside the cluster.** Phase 3 of the backends plan. The owner asked for both HA providers ("support both?"), with Patroni the default. With the `ha` profile and `MDB_K8S_HA_PROVIDER=patroni`, the chart runs the dbpantry-patroni image (the same PostgreSQL and extensions as the standalone image) as a StatefulSet. Patroni uses the Kubernetes API as its DCS: the leader lock and cluster config are ConfigMaps (`<scope>-leader`, `<scope>-config`), so there is no etcd and no HAProxy. A namespaced Role allows only what Patroni needs. The pods are labelled `role=primary|replica`, so Service `pg` follows the primary and `pg-ro` balances over the replicas. With `MDB_K8S_HA_PROVIDER=cnpg`, the chart renders a CloudNativePG `Cluster` instead, plus the same `pg` and `pg-ro` Services, so applications do not change. That needs the operator installed first, and the chart refuses without it. The operator runs CloudNativePG's own PostgreSQL image, not dbpantry-pg. The `backup` profile becomes one CronJob per engine that has a Compose sidecar (pg, mysql, mariadb). Each job runs the same `scripts/backup`, shipped as a Secret bundle, against the engine Service and writes to its own claim `<release>-backups-<engine>`. It prunes with `MDB_BACKUP_RETAIN_DAILY` there, and only there. dbpantry creates the claims itself rather than the chart: on storage classes that bind on first consumer, a Helm-owned claim kept `helm --wait` waiting for a job that runs at 03:00. `make destroy` keeps the claims, as it keeps `pitr` volumes.

Testing on OrbStack and kind 0.33 (with CloudNativePG 1.30.1 on kind only) found these bugs, all fixed with a check that failed first:
- Patroni copied the global `namespace` (`/multidb-server/`, an etcd key prefix) into the Kubernetes DCS, so members looked for `/api/v1/namespaces//multidb-server//` and never elected a leader. It is now set for etcd3 only.
- Patroni reads the token from `/var/run/secrets/kubernetes.io/serviceaccount`, which is under the read-only secrets mount. The mount is now a projected volume with a placeholder at that path, so Kubernetes can mount the token inside it.
- The bundle Secret went over the 256 KiB `last-applied` annotation limit. It is now applied server-side. tar also stopped writing macOS extended attributes into it.
- **pg_hba under `bootstrap:` is written once.** The image's start-up hardening then rewrites `pg_hba.conf` on every container start with no replication rule for other hosts, so after any restart the member refused every replica (`no pg_hba.conf entry for replication`). This was latent in Compose HA too. The rules are now under `postgresql:`, which Patroni rewrites on every start.
- The members' local rule was plain `peer`. `kubectl exec` and `docker exec` run as root, so host-side `make backup`, restore and psql were refused. The members now carry the standalone image's `pg_ident` map (root and postgres to postgres). This affects Compose HA too.
- A new job pod's network can lag its start by a second or two, and the first dump got "Connection refused". The job now waits up to 2 minutes for the database port.
- `make destroy --all` would have deleted the backups claim along with the data. It is now a recovery volume.
- CloudNativePG uses the basic-auth password byte for byte. The file's trailing newline failed SASLprep, so the operator never set the superuser password, and every reconcile logged "encrypting password as SCRAM-SHA-256 failed". The Secret is now built from the file without its newline, through stdin.
- `make down` hibernates the Cluster with `kubectl annotate`, which then owned the annotation, and helm 4's server-side apply conflicted with it on the next `make up`. Now `up` removes the annotation first.
- `make psql` named `/var/run/postgresql`, but CloudNativePG's socket is `/controller/run`. It now honours the pod's `PGHOST`.

Tested for real. Patroni on OrbStack: 3 members, Service routing to the primary and the replicas, graceful and forced pod deletes, and a frozen primary (SIGSTOP of patroni and the postmaster) failing over in 23 s with writes continuing and the old primary rejoining as a replica. Also on OrbStack: backup jobs writing dumps and checksums into the claim, pruning an aged dump while leaving a non-artifact file, host `make backup`, down and up with data kept, and destroy keeping the backups claim. On kind, Patroni repeated up, a backup job, `make backup`, a forced leader delete and destroy. CloudNativePG on kind: up (about 90 s to 3/3), psql, a backup job, `make backup`, a primary delete failing over in 2 s with writes continuing, down (hibernate, volumes kept), up (woken, data back) and destroy. Not tested: real cloud clusters, NetworkPolicy enforcement (neither local cluster enforces it), IPv6 pod networks, synchronous mode, and CloudNativePG password rotation while running. Checks 54 and 55 cover the rendering and the backend against stub kubectl and helm.

**D-66: Incus is a backend through incus-compose, shipped untested.** Phase 4 of the backends plan. incus-compose (lxc/incus-compose) is a drop-in for `docker compose` on Incus: it reads the same Compose files, `.env`, profiles and healthchecks, so `MDB_BACKEND=incus` needs no second description of the stack. `scripts/backends/incus.sh` maps the verbs onto it: `up` is `incus-compose up -d` followed by the same health wait as `mdb_compose_up_wait`; `exec`, `cp`, `logs`, `ps` and `down` are the incus-compose commands of the same name (`exec -u USER` is native); `running` and `health` read `incus list` and the `user.healthcheck.status` key that incus-compose's ic-healthd sidecar writes, in the Incus project named after `COMPOSE_PROJECT_NAME`, where a service's instance is `<service>-1`; `volumes` are the project's custom storage volumes in `MDB_INCUS_POOL` (default `default`). It was not run against a live Incus daemon: none was installed on the development Mac (Incus runs in a Colima VM there) and the low-usage run did not stand one up. Check 58 tests the mapping against stub `incus` and `incus-compose` binaries only; docs/guides/incus.md says so and lists what to verify first. No `compose.incus.yml` overlay was added: incus-compose takes `x-incus` options inline, and which Compose hardening keys it honours (`cap_drop`, `security_opt`, `ulimits`) is unverified, so an overlay written blind could only guess.

**D-67: operators for the other engines are planned, not built.** Phase 5 of the backends plan, delivered as documentation and a values stub only, as the owner scoped the low-usage run. docs/guides/operators.md sets the pattern D-65 proved with CloudNativePG (operator installed by the cluster owner, chart refuses without its CRD, Compose service names kept, passwords from `secrets/`, verbs mapped onto the operator's labels and pause) and lists the candidates per engine: Oracle's MySQL Operator or Percona's for MySQL, mariadb-operator, MongoDB Controllers for Kubernetes or Percona's for MongoDB, and K8ssandra for Cassandra. **D-68: a Go binary, `dbpantry`, ported in front of the scripts; phase 1 is the engine manifest.** The owner accepted the refactor plan's X1 on 2026-11-02 (one static Go binary, Go 1.27, a strangler port that keeps every descriptor, compose file, image, `MDB_` key and make target) and approved phase 1 on 2026-11-04. The plan said this decision would be D-65; D-65 to D-67 were taken by the Kubernetes work in the meantime, so it is D-68. What phase 1 adds:
- **The module is `src/`** (`github.com/simtabi/dbpantry/src`, the org's Go layout): `cmd/dbpantry` only wires the process; cobra lives in `internal/cli` alone; `internal/engine` (descriptors, manifest, chart facts), `internal/config` (the env file and environment, layered with koanf), `internal/endpoint`, `internal/fixture`, and `internal/policy`, whose test forbids `InsecureSkipVerify`, `http.DefaultClient`, the default transport and `pprof`/`expvar` (refactor plan N10, N15). Logging is `log/slog`. The stack is mesobia's (N20) so the shared provider module (D9) composes with both. `go.sum` is committed; nothing else that pins a resolution is.
- **The descriptors stay the source** (plan D2). The binary reads a strict subset of the shell the descriptors are written in and refuses the rest with the file and line: a descriptor bash would read differently from the parser is a failure, not a guess. Check 62 compares every key and value bash sees after `engine_load` with `dbpantry manifest -o tsv` (237 values across six engines today), plus implemented, buildable, the pooler, the CI matrix in both modes and the paradigm vocabulary.
- **The manifest is versioned JSON**, `schema_version` 1: add a field and the version holds; remove, rename or change one and it increments. It carries each descriptor verbatim, so the `MDB_ENGINE_*` keys stay a public interface (N21).
- **Paradigms are mesobia's eight** (N11): relational, document, wide-column, key-value, graph, search, vector, time-series. A primary `MDB_ENGINE_PARADIGM` plus an optional `MDB_ENGINE_PARADIGM_ALSO`, because an engine can serve two (ClickHouse: relational, also time-series, mesobia ADR 0047). Check 31's enum was widened in the same change.
- **Endpoints** (N12, F9): network, published and pooled per implemented engine, computed with `gen-compose`'s own arithmetic and precedence (base plus offset, pooler plus 100; `MDB_PUBLISH` and `MDB_PORT_BASE` from the env file, host-port overrides and `MDB_BIND_ADDR` with the environment first). Every pooled endpoint says `superuser: false`: pgBouncer's auth query excludes superusers and ProxySQL mirrors every user except root. The boot budget is 90 seconds, 300 for a heavy engine, the budgets check 32 already proves; no new descriptor key was invented for it.
- **Principals are paths** (N13): admin is `/run/secrets/<root_secret>`; `--project NAME` adds the app and read-only roles `new-project` creates, with the file names it writes. The second half of N13 (dangerous server features off) lands with each engine wave.
- **Fixtures** (G3, G4): `fixture up` runs `make test-profile`'s commands with the caller's profiles and `fixture down` stops the stack. Only engine and pooler profiles are accepted, because ui, backup, metrics, prod and ha start services with volumes. The test overlay gained MongoDB and Cassandra (tmpfs, `volumes: !override`). FerretDB is left out: it has no image, so `gen-compose` emits no service, and an overlay entry for a service with no image makes Compose refuse the project. Check 66 proves from `compose config` that no fixture service mounts a volume; check 64 proves it on a running stack.
- **Generation** (F1, F3, F12): the CI matrix comes from the binary, with `scripts/ci-matrix` kept as its oracle. `scripts/helm-values` and the Kubernetes backend take the engine list from the descriptors (every implemented engine: the same five) instead of each writing it out. The chart keeps its values file, and `dbpantry manifest check-helm` (check 65) reads it with a YAML parser and fails when it restates a descriptor fact differently, so a descriptor change cannot reach Compose and miss Kubernetes. Check 63 keeps engine lists out of the files phase 1 derives; its one exemption, the backup claims in the Kubernetes backend, follows the Compose backup sidecars, which no descriptor declares yet (phase 6).
- **Not in phase 1**, recorded rather than dropped: certificates for every engine (it changes what `make certs` writes), the HA endpoints (phase 4), generated README and versions tables (phase 2), binary releases (phase 9; until then the binary is built from source and nothing publishes it). No GoReleaser run or tag trigger was added.
- **Rollback** is deleting `src/` and `build/dbpantry`: every script still reads the descriptors itself.

**D-69: pgBouncer serves client TLS with the PostgreSQL certificate, and enforces it under `MDB_TLS_ENFORCE`.** An application on another host (a Laravel app on a web server, its database on a separate server under `PROFILES=pg,pooler,backup,prod` with `MDB_PUBLISH=direct` and a private `MDB_BIND_ADDR`) reaches PostgreSQL through `pg-pooler` on `MDB_PORT_BASE + 100`, and refuses any `sslmode` weaker than `require` to a non-loopback host. The entrypoint wrote no `client_tls_*`, and pgBouncer's `client_tls_sslmode` defaults to `disable`, so that client could not connect at all, while PostgreSQL behind it was already hostssl-only. The spec's TLS sections (decision 5, 9.1) cover the engines and say nothing about the pooler; this closes that gap rather than deviating from anything written.
- **The certificate is reused, not issued.** The pooler already mounted `./certs`; its bootstrap, still root, copies `certs/pg/server.{crt,key}` (then `certs/server.*`, the pg image's own lookup order) onto the `/etc/pgbouncer` tmpfs owned by postgres, for the same reason it reads the password there: the key is host-owned 0600. A client trusting `certs/ca.crt` therefore trusts the pooler. `scripts/certs` adds `DNS:pg-pooler` to the pg certificate's SANs so `verify-full` works by service name.
- **Enforced:** `client_tls_sslmode = require` (plaintext clients refused) and `server_tls_sslmode = require` (the default, `prefer`, would fall back to plaintext without saying so; PostgreSQL is hostssl-only under enforcement anyway, so this turns a silent downgrade into a loud failure). Enforcement with no certificate mounted is fatal at start. **Not enforced:** `client_tls_sslmode = prefer` (TLS when the client asks, plaintext otherwise), server side untouched. With no certificate and no enforcement the pooler stays plaintext-only, so a bare `docker run` and check 33 behave as before.
- **`MDB_EXTRA_SANS` entries that are IP addresses also get an `IP:` SAN.** `.env.example` showed `10.0.0.5` as an example, and it was written as `DNS:10.0.0.5` only; RFC 6125 verification of a client connecting by address matches `iPAddress`. The `DNS:` entry stays, so a certificate keeps its previous SANs plus the new one. Existing certificates gain neither SAN until `make certs-renew`.
- **No new `MDB_` variable.** The pooler reads `MDB_TLS_ENFORCE`, passed through `engines/postgres/compose-pooler.yml`.
- **Proxy mode is unchanged, on purpose.** Under `MDB_PUBLISH=proxy` the layer-4 route for PostgreSQL goes to `pg:5432` and the pooler port is not published at all. Routing the front door to `pg-pooler` instead would need `gen-compose` to know which profiles `make up` will start, which it does not: it generates every service and `scripts/profiles` selects later, so a route to a pooler that is not running would accept connections and drop them. An application that must go through the pooler from another host uses `direct`; docs/runbooks/operations.md says so.
- **Not handled:** `MDB_MTLS=true` makes PostgreSQL require client certificates on hostssl, and the pooler presents none upstream (`server_tls_cert_file` is unset), so mutual TLS and the pooler do not combine yet. This predates D-69.
- **Rotation:** the pooler copies the certificate at start, so after `make certs-renew` it serves the old pair until `pg-pooler` restarts, which drops its client connections. `scripts/certs-renew` says so when the pooler is running.

Check 68 proves it on the wire: under enforcement a plaintext client is refused, `require` and `verify-full` (against `certs/ca.crt`, by the `pg-pooler` name) connect, PostgreSQL reports the pooler's own backend as TLS, and enforcement without a certificate refuses to start; without enforcement plaintext and TLS both connect. It counts its attempts and fails below seven.

Relied on: pgBouncer configuration reference (<https://www.pgbouncer.org/config.html>: `client_tls_sslmode` values and its `disable` default, the requirement that `client_tls_key_file` and `client_tls_cert_file` be set when it is not `disable`, `server_tls_sslmode` defaulting to `prefer`, `client_tls_protocols = secure`) and changelog (<https://www.pgbouncer.org/changelog.html>: 1.26.1 current at 2026-10-14; no `*_tls_*` setting renamed or removed since 1.21; 1.20.0 made `prefer` the server default), libpq SSL support (<https://www.postgresql.org/docs/current/libpq-ssl.html>), RFC 6125 section 6 for name versus address matching.

**D-70: Go dependency floors live in one file, not beside each build-go-tool call.** D-51 rebuilds gosu, rclone and postgres_exporter on a current toolchain and raised vulnerable modules with trailing `module@version` arguments written next to each call. That put the same `golang.org/x/net@v0.60.0` in four Dockerfiles, so CVE-2026-78661 (fixed in v0.62.0) failed the pg, mysql and mariadb builds on every pull request at once, including ones that touched no image.
- **`images/_shared/gotools/floors.txt`** lists `<module> <minimum> <advisory>`. Every Dockerfile that installs `build-go-tool` installs the file beside it, and the helper raises each listed module the tool already depends on to its floor when it resolves an older version. It never downgrades and never adds a module the tool does not use (gosu, which uses none of them, builds unchanged).
- **The comparison is semver, not `sort -V`.** `sort -V` puts a release before its own pre-releases; grpc's floor is a pre-release pseudo-version, so a tool already on `v1.84.0` would have been "raised" backwards. `ver_lt` settles equal bases by the pre-release rule.
- **Trailing arguments still work** (preserve by default), applied after the floors, but check 69 refuses them in a Dockerfile, refuses a Dockerfile that installs the helper without the floors, refuses a floor that names no advisory, and runs the comparator against seven cases including release against pre-release. Proven red for each of those by reintroducing the defect.
- **A new Go CVE is now a one-line change**, and the scheduled build on main (D-71) is where it is expected to surface first.

**D-71: images take their distribution's updates whole, download through one verified helper, and CI gates image findings where they can have been caused.** Three failures in pull request #27, one class each. CVE-2026-109518 in apt, then CVE-2026-78661 in x/net (D-70), failed every pull request, including ones that touched no image, because a pinned base keeps receiving fixes and they were applied one `--only-upgrade` line at a time. A verify run was lost to a reset stream fetching the PGDG key, which had no retry, and whose content nothing checked. And no download (s6-overlay, pg_graphql) was checked against any digest.
- **`mdb-os-upgrade`** (`images/_shared/supply/os-upgrade.sh`) applies every update the base's distribution has published, from the distribution only: apt is pointed at `debian.sources`/`ubuntu.sources`/`sources.list` alone, so PGDG and MariaDB packages have no newer candidate and stay put; microdnf disables `OS_UPGRADE_DISABLE_REPOS` (`mysql*`, as the MySQL image already did); Alpine has no third-party repository here. `OS_UPGRADE_PROBE` names the engine version before and after and fails the build if it moved, generalising the assertion the MySQL image already made. Every image's final stage runs it, except Patroni, which is built `FROM dbpantry-pg` in the same run and inherits it. Digests stay pinned: the base is still exactly what `images/bases.tsv` says, plus its distribution's fixes.
- **`mdb-fetch`** (`images/_shared/supply/fetch.sh`) is the one way a build downloads: curl with exponential-backoff retries on any error, then the URL is looked up in `checksums.txt` and the SHA-256 must match. A key is accepted by OpenPGP fingerprint (`--fingerprint`), since a re-published key changes its digest but not its fingerprint; the PGDG key is `B97B0AFCAA1A47F044F244A07FCC7D46ACCC4CF8`, computed from the key packet. A file whose version comes from the base at build time (the MySQL client RPM) takes `--verified-by` and the Dockerfile runs that check (`rpm --checksig`).
- **CI gates where a finding can have been caused.** `scripts/ci-scan-gate` gates the Trivy scan on the weekly scheduled build of main and on pull requests that change an image input (`images/`, `engines/`, `scripts/build`, `.trivyignore.yaml`, the workflow); other pull requests still scan and print every finding, and do not fail on one. A failed scheduled build opens one tracking issue, or comments on it.
- **Check 70** holds all of it without building: the upgrade runs in every final stage and no `--only-upgrade` remains; nothing downloads with curl or wget directly; every pinned download version has a digest; `--verified-by` has its check in the same RUN; `mdb-fetch` refuses a wrong or missing digest (tested offline over `file://`); one weekly schedule; and the gate tested on a scratch repository. Each rule proven red by reintroducing the defect.
- **Not covered yet:** only the engine images are Trivy-scanned in CI. The pgbouncer, cli and caddy images are built and upgraded the same way but no job scans them.
