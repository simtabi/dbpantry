# Configuration

Everything is configured through `.env`, which `make init` creates from
`.env.example` and never overwrites afterwards.

**`.env.example` is the authoritative reference.** All 126 variables are
documented inline there, next to their defaults, and a check fails the build if
a `MDB_` variable is used anywhere in the repository without being documented
in it. This page explains the shape and the settings worth understanding before
you change them; it deliberately does not duplicate the list, because a second
copy would drift and the check would not catch it.

```bash
grep -A3 MDB_PGBOUNCER_POOL_MODE .env.example
```

## Sections

| Section | Covers |
|---|---|
| Core | project name, timezone, CPU/memory budget, bind address, log rotation |
| Per engine | one block each for PostgreSQL, MySQL, MariaDB, MongoDB, Cassandra, FerretDB |
| Connection pooling | pgBouncer pool mode and sizes — see [pooling](pooling.md) |
| TLS and secrets | enforcement, mTLS, certificate lifetime, secret file paths |
| Backup | schedule, retention, destination, encryption |
| UIs | Adminer, pgAdmin, the Caddy front door, basic auth |
| Scale and HA | Patroni, etcd, HAProxy, synchronous commit |

## Naming

```
MDB_<ENGINE>_<SETTING>     per engine   MDB_PG_VERSION, MDB_MONGODB_HOST_PORT
MDB_<SETTING>              global       MDB_TLS_ENFORCE, MDB_BIND_ADDR
```

`<ENGINE>` is the engine's descriptor name uppercased: `PG`, `MYSQL`, `MARIADB`,
`MONGODB`, `CASSANDRA`, `FERRETDB`. Note PostgreSQL is `PG`, not `POSTGRES`.

## The settings that matter most

### Version selection

```
MDB_PG_VERSION=17
MDB_MYSQL_VERSION=8.4
MDB_MONGODB_VERSION=7.0
```

Each engine's menu is its maintained versions: the newest supported line and
the one before it, listed in [Supported versions](versions.md). Anything off the
menu is refused, unless you also name its upstream image, pinned by digest:

```
MDB_MARIADB_VERSION=11.4
MDB_MARIADB_BASE_IMAGE=docker.io/library/mariadb:11.4.13@sha256:<digest>
```

That version then runs **unsupported**: dbpantry does not build, scan or verify
it, gives no scan guarantee, and `make check-env` warns on every start.

**Data volumes are per engine and per major version.** Switching
`MDB_PG_VERSION` from 16 to 17 does not point PostgreSQL 17 at PostgreSQL 16's
data directory — it gets its own, and 16's is untouched. That is not caution,
it is necessity: PostgreSQL refuses to start against a foreign major, and a
scheme that shared one volume would produce a container that will not boot and
appears to have eaten your data. To actually migrate, see [Upgrade](../runbooks/upgrade.md).

### Ports and exposure

```
MDB_PUBLISH=none        # none | direct | proxy
MDB_PORT_BASE=54000
MDB_BIND_ADDR=127.0.0.1
```

Publishing a host port is the only thing here that can collide with software
you already run, and a collision surfaces as a Docker error at the end of a
boot. So it is a decision:

| Mode | What binds | Use it when |
|---|---|---|
| `none` | nothing | Default. Applications join `mdb_net` and use service names. |
| `direct` | one port per engine | A GUI client that cannot join a Docker network. |
| `proxy` | one Caddy front door | You want a single process owning the host ports. |

In `direct` and `proxy`, a port is `MDB_PORT_BASE + offset`, where the offset is
declared per engine (PostgreSQL 0, MySQL 1, MariaDB 2, MongoDB 3, Cassandra 4,
FerretDB 5). Move the base and every engine follows.

The offsets are explicit rather than derived from each engine's own port,
because MongoDB's 27017 plus a 54000 base is 81017 — past the end of the port
range. Check 31 rejects a duplicate, missing, or out-of-range offset.

`MDB_<ENGINE>_HOST_PORT` still overrides a single engine, but moving the base is
almost always what you want.

`MDB_BIND_ADDR` defaults to loopback. Changing it to `0.0.0.0` publishes every
enabled engine to your network — do not do that as a convenience for a colleague
on the same wifi. On a server, see [Operations](../runbooks/operations.md).

### Projects

```
MDB_PG_DATABASES=app:app_user:__FILE__,analytics:analytics_user:__FILE__
```

`database:username:password`, comma-separated. `__FILE__` is the value you want:
it resolves to `secrets/pg_<user>_password.txt`, so no password is ever written
into `.env`.

Each entry creates the database, an owner role, a read-only companion, and
revokes the default `PUBLIC` grant so roles cannot reach each other's data.
Every engine uses the same format — Cassandra creates a keyspace, MongoDB a
database with a scoped user.

### Secrets

Passwords never appear in `.env`, in a compose file, in an image layer, or in a
log. They live in `secrets/`, which is gitignored, generated by `make init`, and
mounted read-only.

The convention is `_FILE`: the container receives a *path*, reads it, and uses
the value. Check 03 scans every tracked file and fails on a literal credential.

```bash
make rotate-secrets      # rotate everything, applied to running engines
```

### TLS

```
MDB_TLS_ENFORCE=false      # forced true under the prod profile
MDB_MTLS=false
```

Certificates are generated by `make init` and renewed by `make certs-renew`,
which reloads without downtime. With `MDB_TLS_ENFORCE=true` the server refuses
plaintext TCP; unix sockets still count as a secure transport, so local tooling
keeps working. pgBouncer follows the same switch: it refuses plaintext clients
and requires TLS to PostgreSQL, serving `certs/pg`'s certificate (see
[Connection pooling](pooling.md#the-pooler-speaks-tls)).

`MDB_MTLS=true` (with enforcement) adds client certificates. PostgreSQL requires
one whose CN is the role on every direct TCP connection; pgBouncer requires one
issued by the toolkit CA and presents its own, `certs/pooler/client.crt`, to
PostgreSQL. `make certs` issues the pooler's; `make new-project` issues one per
role under `certs/clients/<role>/` when `MDB_MTLS` is on, and
`scripts/certs --client <role>` issues one by hand. `make certs-renew` re-issues
all of them. See [Connection pooling](pooling.md#mutual-tls).

```
MDB_EXTRA_SANS="db.internal,10.0.1.5"
```

Extra names on the generated server certificates, for clients that connect with
`sslmode=verify-full` by a name or address other than the service name. An IP
address is written as both a `DNS:` and an `IP:` SAN. Run `make certs-renew`
after changing it; existing certificates are not re-issued otherwise.

### Resource budget

```
MDB_MEM=4
MDB_CPUS=4
```

Engines tune themselves from these — shared buffers, work memory, the InnoDB
buffer pool — rather than each carrying a separate hand-set number that drifts.
Per-service `_CPU_LIMIT` and `_MEM_LIMIT` caps exist for hard ceilings.

Cassandra is the exception worth knowing: its JVM heap is set explicitly by
`MDB_CASSANDRA_HEAP`, and it will not start meaningfully below about 1 GB.

## Profiles

Profiles decide what runs; `.env` decides how it behaves.

```bash
make up PROFILES=pg,mongodb,pooler,ui
```

Set a default so you can type `make up`:

```
MDB_PROFILES=pg,ui
```

Precedence is `PROFILES=` on the command line, then `MDB_PROFILES` in `.env`,
then `pg,ui`.

The `prod` profile is not a suggestion — it adds guards, and `check-env` refuses
to start if TLS is off, a pooler is missing where one is required, or a UI is
exposed without basic auth.

## Validation

```bash
make check-env
```

Run automatically by `make up`. It checks that sentinel values were replaced,
required variables are set, ports do not collide, versions are on the menu, and
the prod guards hold. It fails loudly rather than starting something misconfigured.

## Overriding engine config files

For settings with no `MDB_` variable, drop a config fragment in
`overrides/<engine>/`. It is mounted read-only into the engine's include
directory and survives upgrades, because it is yours and not generated.

```
overrides/pg/99-local.conf
overrides/mysql/99-local.cnf
```
